# 大白话深读《Helios》

## 1. 30 秒定位

Helios 解决的核心问题是：如何在单张 NVIDIA H100 GPU 上，让一个 14B 参数的大型视频生成模型以可交互速度生成分钟级长视频；论文给出的办法是同时压缩“历史视频”和“待生成噪声”的 token 数，并把 50 步扩散蒸馏到 3 步，代价是分辨率只做到 384×640、部分自动指标与强教师模型打平而非显著超越。论文写明的最亮指标是 Helios-Distilled 在 Table 3 达到 19.53 FPS，并宣称这是首个 14B 模型在单 H100 上达到约 19.5 FPS。需要区分：19.53 FPS 是论文实测数，而“首个”“质量可比”带有作者主张色彩。

## 2. 为什么这篇论文会出现

过去一年 Diffusion Transformer（扩散 Transformer，DiT）在视频生成上进步明显，但主流模型通常只生成 5～10 秒，短片段也可能需要几分钟到几十分钟合成。需求侧来自游戏引擎、交互式生成、世界模型等对实时与长时程的追求，但社区里被标为“实时无限视频生成”的方案多数建立在 1.3B 小模型上，容量不足，难以表达复杂运动、容易丢失高频细节。Krea-RealTime-14B 虽然把模型扩到 14B，却在 H100 上只有 6.7 FPS，且论文称其漂移严重。更关键的是，主流防漂移手段有三类隐形成本：Self-Forcing 这类 train-as-infer rollout 会极大增加训练开销，且鲁棒性耦合于训练 rollout 长度；error-banks、keyframe sampling 等启发式方法要么成本高、要么覆盖不全；因果掩码把双向预训练模型改成单向推理，论文认为牺牲了跨段交互，限制质量。Helios 的作者试图走另一条路：不依赖这些常用技巧，而是从数据表示、位置编码、训练损坏模拟、上下文压缩和多尺度采样四个层面同时下手，让 14B 模型能“以 1.3B 的成本”做长视频续写。

## 3. 方法全景：先看数据流

先画一条简化数据流，再拆组件。文字说明：历史上下文 \(X_{\text{Hist}} \in \mathbb{R}^{B \times C \times T_{\text{Hist}} \times H \times W}\) 与噪声上下文 \(X_{\text{Noisy}} \in \mathbb{R}^{B \times C \times T_{\text{Noisy}} \times H \times W}\) 分别经过时空压缩和多尺度加噪，然后以拼接形式进入 DiT。

```text
提示文本 y ──> Text Encoder ──> KText, VText ──┐
                                               │ (交叉注意力只作用于 XNoisy)
XHist (干净历史帧) ──> Multi-Term Memory Patchification ──> 压缩历史 token ──┐
                                                                       │
XNoisy (当前待生成噪声段) ──> Pyramid Unified Predictor Corrector ──> 多尺度噪声 token ──┤
                                                                       │
              [QNoisy,KNoisy,VNoisy] + [QHist,KHist·amp,VHist] ──> Guidance Attention
                                                                       │
                                                        DiT Blocks ×L ──> 去噪后的 X0^Noisy
                                                                       │
                                                            VAE Decoder ──> 新视频段
```

核心组件逐一拆解：

**Representation Control（表示控制）**：它的输入是拼接的历史上下文 \(X_{\text{Hist}}\) 和噪声上下文 \(X_{\text{Noisy}}\)，输出是“任务自动切换”后的条件表示。具体做法不看图也能复述：训练和推理都保持 \(T_{\text{Hist}} \gg T_{\text{Noisy}}\)；如果 \(X_{\text{Hist}}\) 全为零，模型做 T2V（文本生视频）；如果只有最后一帧非零，做 I2V（图生视频）；否则做 V2V（视频生视频）。目的不是增加额外分支，而是用同一个模型覆盖三种任务，并避免因果掩码对推理范式的改变。

**Guidance Attention（引导注意力）**：这是一个注意力层的结构改造。历史上下文是干净、已对齐语义的，不应被去噪，因此固定其 timestep 为 0；在自注意力中，查询、键、值分别从历史和噪声两个来源计算。历史键 \(K_{\text{Hist}}\) 会先乘以可学习的 head-wise 放大权重 \(amp\)，再与 \(K_{\text{Noisy}}\) 拼接，缩放值也如此。其输出 \(X_{\text{Self}}\) 的形状与拼接 token 序列对应；交叉注意力则只把 \(Q_{\text{Noisy}}\) 与文本键值 \(K_{\text{Text}}, V_{\text{Text}}\) 对齐，避免重复注入历史已经带有的语义。

**Multi-Term Memory Patchification（多期记忆分块）**：压缩历史上下文。把 \(X_{\text{Hist}}\) 按时间远近分为短、中、长三块，各自用不同卷积核做时空下采样；越远的历史用越大的核，保持 token 预算不变。论文给出的参数是 \((p^{(1)}_t, p^{(2)}_t, p^{(3)}_t)=(4,2,1)\)、\((p^{(1)}_h,p^{(2)}_h,p^{(3)}_h)=(8,4,2)\)、\((p^{(1)}_w,p^{(2)}_w,p^{(3)}_w)=(8,4,2)\)，三段帧数为 \((T_1,T_2,T_3)=(16,2,2)\)。Section 4.1 写明这使历史 token 数从 5HW 降到 5/8HW，约 8 倍压缩。

**Pyramid Unified Predictor Corrector（金字塔统一预测校正器）**：压缩噪声上下文。把原本“全分辨率噪声到全分辨率数据”的流匹配轨迹改成“低分辨率噪声到多分辨率数据”的 K 段轨迹，K 实际取 3。早期阶段在低分辨率空间做全局结构去噪，后期升到全分辨率细化细节；阶段之间上采样终端状态并做加噪校正。这一模块让噪声 token 数在 Section 4.1 中从 NHW 降到 7/16 NHW，约 2.29 倍。

## 4. 核心公式与直觉

这里只保留理解贡献必需的两个式子。

**公式 (1)：历史放大的自注意力**

\[
X_{\text{Self}} = \text{Attention}([Q_{\text{Noisy}}, Q_{\text{Hist}}], [K_{\text{Noisy}}, K_{\text{Hist}} \cdot amp], [V_{\text{Noisy}}, V_{\text{Hist}}])
\]

变量解释：方括号拼接；\(Q, K, V\) 分别是查询、键、值张量；\(amp\) 是逐头可学标量，原文称 head-wise amplification tokens。直觉是：历史内容富含上下文信息，但未必所有历史都对当前生成有用，甚至会引入冗余或有害信号，所以给每个注意力头一个独立缩放因子，让模型学会按头挑选历史。工程对应：这替代了因果掩码防止噪声干扰历史的作用，同时保留双向交互，使 FlashAttention 这类高效后端能继续使用。注意，公式本身没有给出 \(amp\) 的维度或初始化方式，论文只是文字说明。

**公式 (5)～(7)：多尺度流匹配**

\[
x^k_t = (1-\lambda_t) x^k + \lambda_t \,\text{Up}(x^{k-1})
\]

\[
v^k = x^k - \text{Up}(x^{k-1})
\]

\[
L = \mathbb{E}_{k,\lambda_t,x^k_t,\text{Up}(x^{k-1}),y}\left[ \| u^k_\theta(x^k_t, y, \lambda_t, k) - v^k \|_2^2 \right]
\]

变量解释：\(k\) 是阶段号，从 1 到 K（本文 K=3）；\(x^k\) 是第 k 阶段的干净目标；\(\text{Up}(x^{k-1})\) 是前一阶段输出的上采样结果；\(x^k_t\) 是带噪中间态；\(\lambda_t \in [0,1]\) 控制噪声水平；\(u^k_\theta\) 是网络预测的速度场；\(v^k\) 是真实速度。公式 (7) 的优化动作是最小化网络速度预测与真实速度的 L2 距离。工程对应：它把流匹配从单尺度扩展到多阶段，使前几段低分辨率步计算量大幅减少，同时定义了一条从低分辨率噪声逐步升采样的直接传输路径。抽取时公式有少量符号丢失，但核心线性插值路径和速度匹配目标仍可辨认。

## 5. 训练与推理怎么跑

### 训练

初始化来自 Wan-2.1-T2V-14B，训练数据为 0.8M 个时长小于 10 秒的片段，分辨率封顶 384×640，每个视频抽取 109 帧片段。训练分三个阶段。

**一轮 Stage 1（Base）的训练 step**：从视频中取一段作为历史上下文 \(X_{\text{Hist}}\)，取相邻后续段做噪声上下文 \(X_{\text{Noisy}}\)；对历史帧用 Frame-Aware Corrupt 按概率加曝光偏移、加噪或下采样，再对 \(X_{\text{Hist}}\) 做 Multi-Term Memory Patchification；把处理后的历史与噪声段拼接进入 DiT，计算流匹配损失。Module 冻结情况：VAE、文本编码器冻结，DiT 通过 LoRA 训练，Rank 128。超参数：全局 batch 128，AdamW lr 5e-5，BFloat16，64 H100，5.5k 步；post 阶段 lr 降到 3e-5，再训 7.5k 步。

**Stage 2（Mid）**：在 Stage 1 基础上加入 Pyramid UPC，把噪声上下文的生成轨迹从单尺度改为 K=3 的多阶段。LoRA Rank 升到 256，batch 先 256 后 192，lr 先 1e-4 后 3e-5，训练步数先 16k 后 20k，同样 64 H100。这一阶段得到 Helios-Mid，优化目标是公式 (7) 的多尺度速度匹配。

**Stage 3（Distilled）**：对 Helios-Mid 做对抗分层蒸馏，教师为 Helios-Base（论文在 3.4.2 曾写作 Helios-Base1，后文表格和正文均为 Helios-Base，疑似笔误）。蒸馏目标包括 DMD 分布匹配项和 GAN 项。teacher 只用真实数据作历史、每步只生成一个 section；用 Staged Backward Simulation 分 K 阶段反向估计 \(x^k_0\)；用 Coarse-to-Fine Learning 的 ODE 初始化和动态加噪调度稳定训练；再加 Adversarial Post-Training 在 pfake 上挂多粒度判别头。训练时 Gθ 每 5 步更新一次 pfake（TTUR），EMA 参数做 ZeRO-3 分片。超参数见表 2：Stage 3 用 128 H100，Gθ lr 2e-6，pfake lr 4e-7，GAN head 层在 DiT 层 5/15/25/35/39 位置，维度 768。训练完成得到 Helios-Distilled。

### 推理

Stage 1 和 Stage 2 的推理：给定提示，编码文本；若 T2V，历史上下文置零；若 I2V，历史上下文只保留首帧；若 V2V，保留真实历史段。随后循环生成后续视频段：每段用 UniPC 调度器、50 步、CFG scale 5.0、v-prediction；历史上下文经过 Memory Patchification 后与噪声段一起注入 DiT。Stage 3 用 Helios-Distilled：3 步采样、x0-prediction、CFG scale 1.0。所有阶段都不使用 KV-cache、稀疏/线性注意力、量化；跨段续写靠的是历史上下文不断前移与新生成噪声拼接。论文还引入 Adaptive Sampling 和 Interactive Interpolation 两个免训练推理技巧：前者在检测到 RGB 统计突变时触发针 Frame-Aware Corrupt 的额外扰动，后者在用户中途改提示时在 M 个中间嵌入上做线性插值。

## 6. 实验和消融证明了什么

| 证据 | 来源 | 结论 | 锚点与限制 |
|---|---|---|---|
| Helios-Distilled 短视频 19.53 FPS，总分 6.00 | Table 3 | 速度快于同尺寸 TurboDiffusion（10.15 FPS）和 FastVideo（5.37 FPS），且得分高于所有蒸馏基线 | 只测 81 帧 384×640；自动指标与人类偏好对齐弱 |
| 长视频 1440 帧综合表现 | Table 4 | Helios-Distilled 总分 6.94 超过 Reward Forcing（6.88），且漂移指标多处于中上 | 正文声称总分为 7.08，但与表格不一致；抽 Table 4 可能列错位，需谨慎 |
| 移除 First-Frame Anchor | Table 5 | 总分从 6.47 降到 5.51，Drifting Naturalness 从 5 降到 2 | 最能证明“色彩漂移锚点”关键的消融 |
| 移除 Frame-Aware Corrupt | Table 5 | 总分降到 4.70，240 帧即出现严重漂移 | 论文明确称该组件最影响抗漂移，Figure 17 定性佐证 |
| Guidance Attention 加因果掩码 | Table 5 | 训练不稳定；移除 Guidance Attention 导致语义累积，总分 6.23 | 论文将“训练不稳定”作为结果而非停训，底因未细给 |
| Multi-Term Memory Patchification | Figure 7 文字 | 历史长度可到 18 而不 OOM，朴素设计 6 段即 OOM | 非定量表，推论来自消融文字 |
| Pyramid UPC | Table 3/4 对照 Helios-Mid 与 Base | 速度从 0.54 增到 1.05 FPS，总分仅小幅下降 | 牺牲少量质量换取约 2×吞吐 |

还需强调三个未完全证明的点：第一，所有自动指标（Aesthetic、Smoothness 等）论文自己也承认与人类感知弱对齐，且消融表中很多指标变化幅度很小；第二，用户研究只有 200 份有效问卷、40 对比/人，未给出置信区间，对“显著更好”支持有限；第三，分辨率锁定 384×640，没有高分辨率实验；此外，长视频 Table 4 的文字总分与表格不一致，需要复现代码验证。

## 7. 与前作怎么选

| 方案 | 规模 | H100 FPS | 防漂移方式 | 训练成本 | 适用场景 |
|---|---|---|---|---|---|
| Krea-RealTime-14B | 14B | 6.74（论文引） | 同类范式但论文称漂移严重 | 未完全披露 | 已开源可比较，但速度低、漂移大 |
| Self-Forcing / LongLive / Reward Forcing | 1.3B | 18～22 | self-forcing + rollout | 自滚动训练成本高 | 小容量、可快速出片，但复杂运动与高频细节受限 |
| Helios-Distilled | 14B | 19.53 | 真实数据历史注入 + Frame-Aware Corrupt + Relative RoPE 等 | 三阶段，蒸馏阶段真实数据单段，无 rollout | 需要 14B 级泛化能力同时单卡实时 |

何时选 Helios：当任务必须在单卡 H100 上实时生成、且时长超过 5 秒乃至分钟级，同时要求比 1.3B 模型更强的运动和视觉保真时，Helios 是目前论文环境下最合适的选择。何时不选：如果目标分辨率必须高于 384×640，或对文本对齐、自然度有更严格要求且能接受慢速大规模模型，或社区已有其他更强推理框架，则不应把它当作唯一基线。论文把 Helios 与 SANA Video Long、LTX Video 2、HV Video、Wan 2.1/2.2 等大量模型做了同日条件对比，但长视频 240/720/1440 帧的对比主要来自同族蒸馏模型，绝对差距不大。

## 8. 工程判断与收束

数据侧：0.8M 片段全部短于 10 秒，说明长视频稳定性主要靠训练时的损坏模拟和位置编码重构获得，而不是大时长真数据拟合；这降低了数据成本，但也意味着分钟级泛化本质上是插值外推，上限可能受预训练短片分布约束。算力/延迟侧：训练要求 64 到 128 张 H100，分三阶段共约 53k steps，硬件成本不低；但推理单卡 19.53 FPS 的测量包含 VAE 和文本编码器，且明确开启了 FlashAttention、torch.compile、KV-cache 等官方加速技术，因此“19.5 FPS”是工程口径，不是纯 DiT 延迟，外界复现需对齐。实现难点集中在 Stage 3 的四模型同卡问题：即便论文声称可容纳四个 14B 模型，训练仍需 128 H100 和异步释放、梯度缓存等技巧，说明单卡集成训练可能受限。最可能失败的环节有两个：一是 Frame-Aware Corrupt 的参数和概率空间很窄，换数据集需要重调；二是 Stage 3 的对抗蒸馏与多尺度 PMC 耦合后，作者自己也报告 Decouple DMD 和 RL 变体都变差，说明这套训练配方对改动敏感。未回答问题包括：高分辨率、长视频记忆、感知对齐指标、段间闪烁、用户研究统计效力。尤其要提醒，Table 4 总分矛盾、以及部分“显著优于”是建立在弱指标的十进制映射上。

读完必须记住的 5 件事：
1. Helios 用 14B 模型在单卡 H100 上跑到约 19.5 FPS，关键靠 History/Noisy 两侧 token 压缩与 50 步→3 步蒸馏，分辨率仅 384×640。
2. 防漂移不是靠 rollout 或 error-bank，而是靠 Relative RoPE、First-Frame Anchor、Frame-Aware Corrupt 三项训练策略。
3. 历史上下文通过 Multi-Term Memory Patchification 压缩约 8 倍，噪声上下文通过 Pyramid UPC 压缩约 2.29 倍。
4. 模型统一支持 T2V/I2V/V2V，任务切换由历史上下文置零或只保留首帧实现，没有额外分支。
5. 所有“质量可比/更强”都建立在论文本人也认为弱对齐的自动指标上，分辨率局限与用户研究小样本是主要限制。
